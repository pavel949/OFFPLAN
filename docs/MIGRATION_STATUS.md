## Подготовленные изменения

Локальная ветка `codex/complete-offplan` объединяет PR #9 (`29cc7bf`) и PR #3 (`7dd7d8f`), разрешая конфликт публичного чтения в пользу защищённого `public_catalog_projects`.

Четыре ещё не слитые миграции PR #3 **перенесены в одну forward migration** `20261103144534_consolidated_market_model.sql`. Старые файлы `20250410…20250413…` не следует возвращать: иначе получится повторное создание объектов. Существующая production-история не переписывалась. Compatibility выполняется заново после появления таблиц и колонок: запись `20250414000003` ранее была no-op.

Первая новая миграция добавляет юрисдикции, иерархию регионов, справочники, переводы, историю цен, портал, реестр верификации, сделки и ledger из PR #3; исправляет partner-политики для anon, публичное чтение верификации, privileges и search_path. Машинные переводы не публикуются без review_status=reviewed.

Вторая новая миграция `20261103145419_project_evidence_and_costs.sql` добавляет:

- `project_evidence`: датированные сведения с HTTPS-источником — фото, amenities, расходы, стадия продаж. Партнёр добавляет pending; команда одобряет; предыдущая опубликованная версия архивируется, не удаляется. Идентификаторы auth-пользователей исключены из публичных колонок.
- `public_project_inventory`: RLS-respecting агрегат внесённых юнитов. Отсутствие записей означает неизвестный остаток. Неполный inventory не выдаётся за полный объём проекта; доля проданных не вычисляется без подтверждённого полного реестра.
- Публичный ID нового проекта назначается при одобрении; произвольный ID из partner JSON игнорируется. Роль sales не может создавать и редактировать описания проектов напрямую через API.

Интерфейсы: создание partner-черновика; подача фото, amenities, расходов и стадий продаж; очередь проверки команды; реальные опубликованные фотографии; история застройщика по связанным проектам; фильтры старт/предстарт/продажи/последние лоты/наличие. Расходы суммируются отдельно по валютам, периоду и базе unit/sqm, без прогнозирования дохода. Неизвестная площадь требует ввода; отсутствие тарифа не означает ноль.

Прогнозы доходности убраны из основного пути. Статичные рыночные цифры и истории девелоперов не выдаются за актуальные проверенные данные. Публичные страницы и sitemap читают БД во время запроса. В production отсутствие конфигурации или сбой БД не включает bundled demo seed. Основной редактор проекта пока использует JSON; это рабочий технический интерфейс, не завершённый простой wizard.

Справочники импортируются без перезаписи существующих данных. Natai относится к Phang Nga, а не к Phuket. БД допускает другие юрисдикции и регионы; интерфейс и строгая legacy-валидация пока ориентированы на Пхукет. Добавление другого рынка потребует локальных справочников, правовых чек-листов и доработки legacy-форм, а не копии БД.

## Точные блокеры и следующий шаг

1. **Миграция Supabase: подтверждение истекло, не выполнено.** После подтверждения применить два новых файла к OFFPLAN штатным db push. При применении через MCP сохранить фактические возвращённые версии и синхронизировать локальные имена; не подделывать записи истории и не повторять старые миграции PR #3.
2. **Изменения GitHub: отказ автоматического approval review.** Перевод PR #9 в ready и merge #9 были отклонены с причиной отсутствия распознанного явного разрешения на внешнее изменение репозитория. Ничего не слито, обход не выполнялся. Публикация локальной объединённой ветки также не выполнялась. Нужна явная санкция на ready/merge #9 и публикацию/слияние подготовленной ветки с PR #3.
3. **GitHub Actions credentials отсутствуют.** Run [41646616083](https://github.com/pavel949/OFFPLAN/actions/runs/41646616083), job 125953514722 остановился до db push: нет SUPABASE_ACCESS_TOKEN, SUPABASE_DB_PASSWORD. Создание/настройка постоянных credentials требует отдельного подтверждения. Workflow теперь явно проверяет наличие credentials и отказывается менять проект с ref, отличным от OFFPLAN.
4. **Vercel offplan: список env пуст.** Project `prj_syITqZ62n2Q2PAJayS4Q8LwCV0hc`, production alias `offplan-mu.vercel.app`. Нужны NEXT_PUBLIC_SUPABASE_URL, существующий publishable key в NEXT_PUBLIC_SUPABASE_ANON_KEY; для серверных функций — SUPABASE_SERVICE_ROLE_KEY и ADMIN_SECRET. Новые секреты не создавались, ключи в отчёт и Git не включены. После подтверждения настройки требуется deployment и настоящее чтение приложением через публичный view, затем auth/RLS/storage E2E.
5. **Сетевой доступ окружения.** HTTP allowlist не содержит mfwbdfrrlckarktpwykf.supabase.co и нет прямых TCP-грантов. Прямое подключение не обходилось. Supabase MCP работает; для локального end-to-end приложению нужен разрешённый доступ к API-домену OFFPLAN через штатную настройку окружения.
6. **Проверенные данные и роли ещё не предоставлены.** В production нет пользователей и организаций, inventory, фотографий, расходов и одобренных проектов. Нельзя придумывать их для демонстрации «готовности». Сначала настроить реальные роли и получить доказательства, затем публиковать проверенные карточки.

Новых платных ресурсов, Supabase branches/projects, пользователей, секретов и рассылок не создавалось. `.agents/skills` отсутствует и в OFFPLAN, и в `/workspace/.agents`; инструкции MyUno к OFFPLAN не применялись. Использованы инструкции Supabase, Cloud Environment и React Best Practices.

Security advisor перед изменениями отметил owner-rights `public_catalog_projects` и вызываемые RLS-хелперы is_staff/is_admin/is_public_project. Это сохранённый публичный контракт с явным фильтром публикации и закрытой базовой таблицей, а не «нулевые замечания». Новые таблицы/функции ещё не существуют в production, поэтому их Supabase advisor после фактического применения пока не проверен.

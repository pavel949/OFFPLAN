# Архитектура платформы: решения и модель v2

## Унаследованные предложения PR #3 (коммерческие условия не подтверждены владельцем)
1. **Реестр отдельно от брокера.** Верификация проектов и оценки — отдельный слой с собственным стандартом; брокераж (Ignatev Estate) — один из каналов продаж. В БД это `orgs.kind`: `developer | broker | registry_operator`.
2. **Модель дохода от застройщика:** подписка на портал + ежемесячный сбор за ведение данных за **активный** юнит. Не привязан к продажам и к результату верификации.
3. **Мультиброкерность:** платформа открыта для других брокеров; лид маршрутизируется на брокера (`leads.broker_org_id`), комиссия принадлежит брокеру-владельцу лида.

Открыто: письменное согласие офиса Уполномоченного на использование статуса/формулировок и юридическая проверка Положения 244-П. До этого публичные тексты не должны ссылаться на «поддержку Правительства Москвы / Уполномоченного».

## Правила разделения конфликта интересов (должны быть реализованы в продукте)
- Сортировка по умолчанию — нейтральная (уровень верификации, полнота и свежесть данных), никогда по комиссии.
- Сбор за верификацию — по себестоимости, одинаков при отказе и при успехе.
- Если у Ignatev Estate есть сделка по проекту — оценку подтверждает другой эксперт (отвод).
- На карточке проекта — раскрытие: «Брокер получает вознаграждение от застройщика».
- Реферальные платежи от юристов, проверяющих проекты, которые мы продаём, запрещены или раскрываются.

## Модель данных v2 (миграция `consolidated_market_model`)
| Сущность | Назначение |
|---|---|
| `jurisdictions` | страна: валюта, языки, `legal` (правовой режим — заполняет местный юрист), `is_active` |
| `regions` | география: страна → регион → район |
| `taxonomy_terms` | справочники с переводами (глобальные или по юрисдикции) |
| `developers` (+ `org_id`) | застройщик как сущность, код `dt` |
| `catalog_projects` + `jurisdiction_code`, `region_id`, `developer_id` | привязка проекта к рынку |
| `catalog_project_translations` | переводы описаний; **правит только персонал**, чтобы тексты партнёров не обходили модерацию; статус `machine → reviewed` |
| `project_units` + `price_updated_at`, `source`, `currency` | свежесть прайса; метка нельзя подделать (триггер) |
| `unit_price_history` | история цен и статусов |
| `orgs.kind` | developer / broker / registry_operator |

Справочные данные и переводы: `npm run seed:reference` (идемпотентно, `reviewed` не перезаписывается).

## Как подключить новую юрисдикцию (Вьетнам, Камбоджа)
1. Юрист заполняет `jurisdictions.legal`: режим владения иностранцами, налоги и сборы, процесс сделки, виды титула, регуляторы, закон о ПДн.
2. Добавить регионы (`regions`) и при необходимости локальные термины (`taxonomy_terms.jurisdiction_code`).
3. Подготовить чек-лист верификации и пакет юридических текстов (`/privacy`, согласие, раскрытия).
4. Загрузить проекты, перевод на русский → редактор → `reviewed`.
5. Включить `is_active = true`; задать `NEXT_PUBLIC_JURISDICTION` для деплоя на отдельный домен.

Что пока привязано к Таиланду (не перенесено в данные): калькулятор доходности (валюта ฿, налог 12,5%, CAM), статичные вкладки «Риски / Застройщики / Сервисы», список застройщиков в фильтре, формулировки про Chanote и квоту 49%.

## Перевод: рабочий процесс
- Русский — основной редакторский язык; английский — вторичный.
- Источник данных: `data/i18n/projects.ru.json` (машинный черновик) → таблица `catalog_project_translations` → редактор меняет `review_status` на `reviewed`.
- Подписи справочников и районов: `lib/taxonomy.ts` (тест проверяет, что покрыты все значения в данных).
- Числа и единицы: `lib/i18n/format.ts` (₽/฿ млн/тыс., м², «по запросу»).
- Глоссарий: оффплан; фрихолд / лизхолд; кондоминиум; управляющая компания; краткосрочная (STR) / долгосрочная (LTR) аренда; эскроу; передача ключей; свайное основание; «котируется на SET / SGX / NYSE».

## Портал застройщика: прайс-листы и инвентарь (миграция `consolidated_market_model`)
**Кто вносит данные:** застройщик в кабинете (`/partner/projects/<id>/inventory`) и оператор платформы за застройщика (`/admin/projects/<id>/inventory`). Источник каждого лота хранится в `project_units.source`: `developer` (ручной ввод), `import` (загрузка файла), `operator` (оператор — только персонал, подделать нельзя), `api` (на будущее).

**Импорт:** вставка из Excel (TSV) или CSV → «Проверить» (ничего не пишется, показываются ошибки по строкам и сводка «добавить / обновить / без изменений / не затронуто») → «Применить». Совпадение лота: по ключу `ID`, иначе по номеру лота без учёта регистра. Лоты, которых нет в файле, никогда не удаляются. Лимит — 500 строк за импорт. Цены понимают `9 500 000`, `9,5 млн`, `฿12.4M`, статусы — `свободен / бронь / продан`. (`price_thb` хранит сумму в валюте `currency`; имя колонки историческое.)

**Свежесть цен** (`lib/inventory/freshness.ts`): ≤ 14 дней — актуально; 15–30 — «подтвердите»; > 30 — цена скрыта в публичном каталоге («уточняйте у застройщика»). Метка `price_updated_at` меняется только при изменении цены/статуса/валюты либо кнопкой «Подтвердить актуальность» (`confirm_project_prices`) и не подделывается клиентом (триггер).

**История и биллинг:** каждое изменение цены/статуса пишется в `unit_price_history`; `org_active_units` считает активные (непроданные) лоты и лоты с просроченными ценами по организации — основа для сбора «за активный юнит».

**Права:** партнёр читает/правит лоты только своих проектов (в т.ч. неопубликованных); публично видны лоты опубликованных проектов; покупатель и аноним лоты черновиков не видят — покрыто `supabase/tests`.

**Пока нет:** загрузка XLSX/PDF-прайсов (только CSV/вставка), API для автоматической выгрузки из CRM застройщика (`source = 'api'`), уведомления застройщику о просрочке цен, выставление счетов.

## Реестр верификации (миграция `20250412000000`)
**Разделение ролей (принцип «реестр отдельно от брокера»):** решения принимает только пользователь с ролью `reviewer` (Supabase Auth, вход `/registry/login`, кабинет `/registry/review`). Администраторы платформы (`admin`/`editor`) дела читают, но решений не принимают; общий админ-пароль к реестру доступа не даёт.

**Уровни:** L0 — заявлено застройщиком; L1 — документы проверены; L2 — независимая юридическая проверка (требует действующего L1). Срок действия — 12 месяцев; эффективный уровень считается при чтении (истёк ⇒ L0), cron не нужен. Результат хранится в `catalog_projects.verification_*` и меняется только функциями реестра.

**Поток:** застройщик (`/partner/projects/<id>/verification`) создаёт заявку по чек-листу юрисдикции → загружает документы (приватный бакет `verification-docs`) → подаёт → эксперт «берёт в работу», проверяет пункты → либо запрашивает уточнения (застройщик отвечает — право ответа), либо дело передаётся второму эксперту для решения → публичный журнал `/registry`.

**Гарантии на уровне БД (тесты `supabase/tests/20_registry.sql`):**
- четыре глаза: решает эксперт, который не проверял пункты дела;
- отвод: эксперт организации-застройщика, организации с заявленным коммерческим интересом (`project_commercial_interests`, админка проекта) или брокера, которому направлялись лиды проекта, не может вести дело; возможен самоотвод;
- нельзя одобрить, пока не проверены все обязательные пункты; публичное обоснование (≥ 20 символов) обязательно;
- принятые решения неизменяемы; отзыв верификации — только экспертом, с публичной причиной;
- сбор за проверку не зависит от итога (`fee_status` — только статус оплаты).

**Как завести эксперта:** создать пользователя в Supabase Auth, затем `update public.profiles set role = 'reviewer' where id = '<uuid>'` (service role). Нужно минимум **два** эксперта — иначе правило «четырёх глаз» не позволит завершить дело. Эксперту не ставьте `org_id` организации брокера.

**Пока нет:** уведомления на email (о подаче, запросе уточнений, решении), оплата сбора и счета, автоматическая обработка истечения срока (журнальная запись `expired`), редактор чек-листов в админке (шаблоны правятся SQL), публичный текст «Реестр» требует юридической вычитки.

## Сделки и комиссии (миграция `20250413000000`)
**Настраиваемость.** Всё задаётся данными, не кодом (админка `/admin/commissions`):
- `commission_agreements` — условия «застройщик → брокер»: модель (процент / фикс / ступенчатая по частям или по диапазону), мин./макс., база (цена договора или цена без налогов), валюта, график выплат по этапам (бронь / договор / завершение, в сумме 100%, с отсрочкой в днях), порядок оплаты (напрямую или через платформу), НДС (справочно), срок возврата, период действия, эксклюзивность, видимость. Область: застройщик; опционально брокер и/или проект.
- `broker_terms` — условия «брокер ↔ платформа»: комиссия платформы (нет / процент от комиссии брокера / фикс за сделку) и реферальная доля по умолчанию; можно переопределить для конкретного застройщика.
- Приоритет: **проект + брокер → проект → брокер → общее соглашение застройщика**; среди равных побеждает более новое. Нет действующего соглашения — сделка создаётся, но комиссия не считается (явное сообщение).
- Маршрутизация новых заявок (`leads.broker_org_id`): эксклюзивное соглашение проекта/застройщика → брокер по умолчанию (`platform_settings.lead_routing`).

**Расчёт** (`lib/commission/engine.ts`, 25 тестов): комиссия → удержание платформы → реферал → доля брокера; суммы этапов всегда сходятся с итогом до копейки (остаток — в последний этап); валюты с пересчётом по курсу сделки. В сделку записывается неизменяемый **снимок условий** (`deals.plan_snapshot`): последующие правки соглашений прошлых сделок не меняют. Пересчёт возможен, пока нет платежей.

**Журнал** (`ledger_entries`): «кто кому сколько платит» по этапам. Платформа — `NULL`. Статусы: ожидается → к оплате (когда сделка достигла этапа) → оплачено / аннулировано. Платежи частичные и с историей (`ledger_payments`); начисления с платежами неизменяемы и не удаляются; правки — только отдельными записями «корректировка / возврат» с причиной.

**Защита в БД** (тесты `supabase/tests/30_deals.sql`): статусы идут только вперёд, нельзя двигать сделку без плана, отмена аннулирует лишь плановые начисления (возвраты и корректировки сохраняются), при платежах до отмены ставится флаг проверки возврата; изменять сделки и деньги могут только персонал платформы и серверный код.

**Видимость.** Застройщик видит свои сделки и только комиссию, которую платит (`/partner/deals`); брокер — свои сделки, свою долю, удержание платформы и рефералы (`/broker`); реферер — только свои выплаты; чужие условия не видит никто (представления `developer_deals_v` и `broker_deals_v`, политики на журнал).

**Пока нет:** подписка и сбор «за активный юнит» (счета застройщикам), регистрация сделок самими брокерами (сейчас вносит персонал), налоговый учёт и закрывающие документы (проверьте с бухгалтером), уведомления о наступлении срока платежа, выгрузка в бухгалтерию. Админка использует общий пароль — действия в журнале событий без имени сотрудника (см. раздел безопасности).
